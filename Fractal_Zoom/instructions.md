## 2. The project in short

The Mandelbrot set is computed per pixel. Pixel (i, j) is a complex number c. Repeat z = z^2 + c from z = 0 until |z| > 2 or the iteration limit is reached; the iteration count gives the colour. A zoom movie renders many frames while the view window shrinks towards a point.

Every pixel is independent, so the problem is easy to parallelize, but the work per pixel is very uneven: pixels inside the set run to the iteration limit, pixels outside stop early. Equal-sized blocks therefore give some workers much more work than others. The project is a study of load balancing, and its output (a movie) is visible.

Versions to implement:

| Version | Execution model | Deployment | Technologies |
| --- | --- | --- | --- |
| V0 | Serial baseline | one machine | Python + Numba `@njit` |
| V1 | Shared-memory threads | one machine | Numba `prange`, OpenMP threading layer if available. Variant A: prange over rows. Variant B: prange over shuffled tiles |
| V2 | MPI (S1, S2, S3) | VMs with bridged LAN IPs | mpi4py + Open MPI or MPICH |
| V3 | MPI (S1, S2, S3) | Docker containers with LAN IPs | mpi4py, Docker, macvlan or overlay |
| V4 | MPI (S1, S2, S3) | physical machines on a LAN | mpi4py + Open MPI or MPICH |

MPI strategies:

| Strategy | Description | Expected by the proposal (to be verified, not assumed) |
| --- | --- | --- |
| S1 static rows | each rank renders an equal block of rows | poor balance, ranks holding interior rows finish last |
| S2 master-worker tiles | rank 0 gives one tile at a time to whichever worker is idle | good balance, master can become the bottleneck with many workers or tiny tiles |
| S3 frames per rank | each rank renders whole frames | good balance if frames cost about the same, no communication during rendering |

Only rank 0 writes images. File output is timed separately from rendering.

## 5. Code requirements

### 5.1 Core (`src/fractal_core.py`)

One kernel, shared by every version. V0, V1, S1, S2 and S3 must all call the same function and differ only in who calls it and for which block of pixels.

Pitfalls that would break the identity check, and what to do about them:

- **Coordinates from global pixel indices.** The starter code in the proposal computes `x = x0 + (x1 - x0) * i / w` from the tile bounds. If every tile computes its own bounds, floating-point rounding can differ by one unit in the last place compared with the full frame, and a boundary pixel can get a different count. Compute per frame once `xmin`, `ymax`, `dx`, `dy`, then each pixel uses `cr = xmin + i * dx` and `ci = ymax - j * dy` with the global column `i` and global row `j`, whatever the tile.
- **No `fastmath`.** Do not enable it in any kernel.
- **Orientation.** Row 0 is the top of the image and has the largest imaginary part. Add a test that, in frame 0, the real axis (Im = 0) is in the lower half of the image (row > H/2), which is true because the centre has Im > 0. (The starter code maps row 0 to the smallest y, which gives a vertically mirrored picture.)
- **Edge tiles.** When W or H is not a multiple of the tile size, the last tiles are smaller. The starter master-worker code does not handle that (it assumes full tiles). Use `nx = ceil(W / tw)`, `ny = ceil(H / th)` and clip.
- **Cross-machine caveat.** Different CPUs can compile to slightly different floating-point code. On a real LAN with different machines the hash check may fail on a few pixels. If that happens, report it, do not hide it.

Reference shape of the kernel (adapt, keep the idea):

```python
@njit(cache=True)
def render_block(row0, row1, col0, col1, xmin, ymax, dx, dy, maxit):
    out = np.empty((row1 - row0, col1 - col0), np.int32)
    for j in range(row0, row1):
        ci = ymax - j * dy
        for i in range(col0, col1):
            cr = xmin + i * dx
            zr = zi = 0.0
            k = 0
            while k < maxit and zr * zr + zi * zi <= 4.0:
                zr, zi = zr * zr - zi * zi + cr, 2.0 * zr * zi + ci
                k += 1
            out[j - row0, i - col0] = k
    return out
```

Also in this file: `load_config()`, `frame_params(k)` (returns xmin, ymax, dx, dy, maxit for frame k), `maxit_for_frame(k)`, tile list helpers, `row_block(rank, p, H)` (the first `H % p` ranks get one extra row), a hash helper (`sha256` of the int32 array bytes).

### 5.2 Serial V0 (`src/serial.py`)

- Warm-up call on a tiny block before timing (Numba compile time must not be in the measurement).
- Renders all frames (or `bench_frame_indices`), returns the counts, prints and saves the timing.

### 5.3 Threads V1 (`src/threads.py`)

- `@njit(parallel=True)` with `prange`. Set the thread count with `numba.set_num_threads(p)` and check `numba.get_num_threads()`. Set `NUMBA_NUM_THREADS` to the logical core count at process start.
- Try `NUMBA_THREADING_LAYER=omp` (must be set before Numba compiles any parallel function). If it is not available, use `tbb` or `workqueue`. After a parallel call, read `numba.threading_layer()` and record the layer that was really used. Never write "OpenMP" in the report if another layer was used. If it is easy, also run Variant A with a second layer and say whether the layer changes the result (the layers schedule iterations differently). If your Numba version has `numba.set_parallel_chunksize`, you may test it on variant A as an extra, not required.
- Variant A: `prange` over rows. Variant B: `prange` over tiles, the order of the tiles shuffled with the fixed seed so that cheap and expensive tiles are mixed (use 20 and 40 pixel tiles at least, all four sizes if time allows). Each tile writes its own slice of the output array, so there is no race.
- Compare A and B for every thread count. Per-thread busy time is not available inside `prange`; do not invent it. Say it in the report, and use the cost proxy computed from the counts (sum of iterations per row block or tile) to discuss the expected imbalance. Label it clearly as "derived from iteration counts, not measured time".

### 5.4 MPI common rules (S1, S2, S3)

- Each rank runs Numba with one thread (`NUMBA_NUM_THREADS=1`, `OMP_NUM_THREADS=1` set before importing numba), otherwise the comparison with MPI is unfair.
- Before MPI jobs, run `scripts/warmup.py` once so the Numba cache exists. Inside each job every rank also does a warm-up call on a tiny block, then `comm.Barrier()`, then the timer starts.
- Use `time.perf_counter()` or `MPI.Wtime()`. Definitions (write them in the report):
  - `t_render` = from the barrier until rank 0 holds all counts in memory. It includes communication.
  - per rank: `t_compute` (time inside the kernel), `t_wait` (time blocked waiting for a message or at a collective), `t_total`.
  - `t_io` = colour mapping, PNG writing, movie assembly. Measured only in the production run (section 6, E10), never mixed with `t_render`.
- Only rank 0 writes files. Per-rank statistics are collected on rank 0 with a small `comm.gather` and written to the CSVs. No other rank touches the results files.
- Identity check, outside the timed region: rank 0 computes the sha256 of each assembled frame and compares with `results/serial_hashes.csv`. The result goes in the `checksum_ok` column. A mismatch must be loud (non-zero exit code and a line in the log).
- Each script prints one summary line to the console and appends to the results CSV (schema in section 6).
- A hard timeout per run in the runner, so a deadlock cannot block everything. A timed-out run is recorded as FAILED, not skipped silently.
- You may use the pickle-based lowercase `send/recv` (as in the starter code) for control messages. For pixel arrays you may use the uppercase buffer versions. Start with the simple version, make it correct, optimise only if time remains, and report which one was used.

### 5.5 S1 static rows (`src/mpi_s1_rows.py`)

### 5.6 S2 master-worker tiles (`src/mpi_s2_tiles.py`)

Start from the starter skeleton of the proposal and fix what it lacks:

- The task queue covers all frames (task = frame, tile row, tile column), in frame order, so there is no barrier between frames. Document this choice.
- Edge tiles (see 5.1). Requires p ≥ 2 (the master only distributes and assembles, it does not compute). The compute workers are p − 1. For this reason S2 has no p = 1 point; speedup is always computed against the serial V0 time (see 6.2) and you also give the efficiency based on the number of workers.
- Initial distribution when there are fewer tasks than workers, clean STOP messages, no deadlock.
- Record per worker: tiles done, `t_compute`, `t_wait` (time blocked in the receive for the next task), `iterations_sum` (sum of counts of its tiles). For the master: `t_total`, time spent blocked in `recv`, number of messages. These show whether the master is a bottleneck (workers waiting a lot while the master is never blocked).
- Count messages and bytes. The tile-size study (10, 20, 40, 80) must show the trade-off between balance and number of messages, using measured numbers.
- Tip for Open MPI: a blocked `recv` busy-polls and keeps a core at 100 percent, so the master takes a core even when idle. Mention it if p equals the core count. `--mca mpi_yield_when_idle 1` is one thing you may test, as an extra.

### 5.7 S3 frames per rank (`src/mpi_s3_frames.py`)

Each rank renders whole frames, no communication while rendering, then the frames are sent to rank 0 at the end (this transfer is timed as communication). Implement two static assignments: block (rank r gets a contiguous range of frames) and cyclic (frame k goes to rank k mod p). Because the iteration limit grows with the frame index, the frames do not cost the same; measure both assignments and let the data decide. Optional, only if everything else is finished: dynamic assignment of whole frames.

### 5.9 Ping-pong (`src/pingpong.py`)

### 6.2 Definitions (use exactly these, write them in the report)

- `T_serial` = median `t_render` of V0 on the same workload.
- Speedup `S = T_serial / T_p` for every version and strategy (the proposal writes T1 / Tp; V0 is the true single-process baseline, and S2 cannot run with p = 1). Also report each strategy's own p = 1 time where it exists, so the reader can see the parallel overhead at p = 1.
- Efficiency `E = S / p`. For S2 also `E_workers = S / (p - 1)`.
- Frames per second `fps = frames / t_render` (rendering and communication only). The production run gives a second figure that includes `t_io`.
- Load imbalance for a set of ranks: `max(t_compute) / mean(t_compute)`. Say it in the report as a ratio computed from `busy_time.csv`.
- Use median and min–max over repetitions. Do not claim statistical significance.

## 9. The LaTeX report

### 9.1 Format

- `report/main.tex`, class `article`, 11 pt, A4, normal margins (about 2.5 cm). Standard packages only (graphicx, booktabs, geometry, hyperref, amsmath, caption, subcaption, listings; no `minted`, it needs shell-escape). Check that every package is installed before using it. Paths with forward slashes (`\graphicspath{{../figures/}}`).
- Page 1 is the cover page (section 1). After it: the body, at most 6 pages (the proposal asks 4 to 6 pages). Then references, then appendices (extra figures, full tables, environment, commands), which do not count in the 6 pages. Appendices stay short and useful.
- `\input{generated/numbers.tex}` and the generated tables. The bibliography is a manual `thebibliography` environment (no BibTeX).
- Short code excerpts only (the kernel, about 15 lines, is enough). Everything else is referred to by file name.

### 9.2 Content (in this order)

1. **Introduction.** The problem, why the work is uneven, the objectives. Short.
2. **Implementation.** The kernel and the zoom (formulas, the global-index coordinates and why, the iteration limit schedule, colour mapping); V0; V1-A and V1-B; S1, S2, S3 (block and cyclic); how correctness is checked. For every decision: what, why, and in which file. This is the part where the professor sees that the students understood their own code.
3. **Experimental setup.** Machine and software (from `environment.json`), parameters (table), methodology (warm-up, repetitions, median, definitions of `t_render`, `t_io`, speedup, efficiency, imbalance), any deviation from the proposal (reduced benchmark frames, missing p values...).
4. **Results and analysis.** Correctness; threads A versus B; MPI scaling; load balance per worker; tile-size study; S3 block versus cyclic; communication (ping-pong); deployment targets (status table, Docker if run); the movie (sample frames, production timings with `t_io` separate). For each result: what the figure shows (numbers via macros), why (hedged when not tested), and whether it matches what the proposal expected.
5. **Limitations and what did not work.** Real content from `dev_log.md` and from the data (single machine, core counts and hyper-threading, background load, noise, threading layer actually used, no per-thread time in `prange`, what was not run, what is uncertain).
6. **Conclusion.** Short, only what the data support. At most four sentences about what could be done next.

Questions the analysis must answer with evidence from the data (not from general knowledge only): why uneven work hurts static partitioning (cost per row block, cost per tile); at which tile size or process count the master of S2 starts to limit the speed, and the evidence (worker wait share, number of messages); why the speedup stops growing around the physical core count; whether S3 is balanced given that the iteration limit grows with the frame index, and whether block or cyclic is better; whether V1-A or V1-B is better and what the threading layer has to do with it; why VMs or containers on one host cannot scale beyond the host cores.

### 9.3 Writing style

The report is signed by two 5th-year engineering students and must read like their own work.

- Plain, clear English. Short and medium sentences, a longer one now and then. "We" for the authors. Past tense for what was done, present tense for what a figure shows.
- Say things directly and give the reason right after ("because", "so"). Prefer a concrete statement tied to a figure or a file ("S1 is the slowest because the middle row blocks cost more, see Figure 4") over a general statement.
- Be modest where the data is thin ("this suggests", "we did not test this, but we think..."). Do not oversell.
- No marketing tone, no filler. Avoid the words and habits that make text sound generated: delve, crucial, pivotal, robust, leverage, seamless, comprehensive, holistic, "plays a key role", "it is worth noting", "in today's world", "in conclusion", chains of Furthermore / Moreover, rhetorical questions, bold text inside paragraphs, emojis, and em-dashes (use commas or brackets).
- Do not make everything symmetrical: sections can have different lengths, not every paragraph needs a closing summary sentence, not every list needs three items.
- Describe only real problems: anything that "went wrong" must be in `dev_log.md`. Never invent difficulties, anecdotes or lessons learned.
- Do not add typos or deliberate mistakes. The goal is an honest and plain report, not an imperfect-looking one.
- The same plain style applies to code comments, `README.md` and `notes.md`.
